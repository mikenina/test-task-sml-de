# Архитектура решения (to be)

## Границы решения
Решение дано для объемов данных, заданных по умолчанию в synthetic.sql (300000 строк в таблице сделок).

Решение представляет собой процесс ETL массовой загрузки данных из источника в витрины.

Запуск доступен в двух режимах:
1) Регулярный сбор новых\измененных (и новых) данных.
2) Перезаливка сделок с loading_date в интервале `[interval-start, interval-end)`.

### Регулярный сбор измененных (и новых) данных

```bash 
docker compose exec app python -m etl.main --run-type incremental --as-of 2026-10-26
```
* пример использования: ночной запуск по крону `--as-of <today>`;
* выборка данных в источнике происходит по условию `updated_at >= as_of - 1 day` (для упрощения считаем, что у новых сделок `updated_at=created_at`);
* таким образом, ETL обработает все созданные/измененные вчера сделки.

### Перезаливка сделок с loading_date в интервале

```bash 
docker compose exec app python -m etl.main --run-type backfill --as-of 2026-10-26 \
    --interval-start 2026-01-01 --interval-end 2026-02-01 
```
* пример использования: из-за ошибки витрина за прошлый месяц отображает неполные данные. Техподдержка вручную запускает перезаливку.
* перезаливка сделок из источника с `loading_date` на интервале `[interval-start, interval-end)`
* выбирает из источника сделки по loading_date, минимальный объем загрузки - 1 день, максимальный - 5 лет.

В данном решении может быть запущен только один экземпляр процесса. То есть повторный запуск `etl.main` возможен, но только после перехода предыдущего запуска в `success`|`failed`.

## Архитектура

DWH расположен в той же бд, что и источник - БД deals_bigdata (для простоты).
DWH состоит из 4-х слоев: **raw, core, mart, data quality**.

Один запуск ETL за интервал - запускает последовательные синхронные переносы данных `source -> raw -> core -> mart`.
Статистика запусков и сделки, не прошедшие валидацию, фиксируются в слое **dq**.

Возможные статусы ETL процесса: `running / success / failed`.
Статус ETL фиксируется в `dq.etl_runs`. Частичный gist-constraint на этой таблице препятствует запуску параллельных ETL-процессов.

Каждый новый запуск ETL - это новый `run`. Перезапуск упавших `run` в этом решении не предусмотрен.

## Этап source -> raw
[loader_raw.py](../etl/loader_raw.py)

* В слое raw храним снимки состояния источника на момент запуска конкретного ETL с версионированием по run_id.

* В данном решении для простоты снимки хранятся в postgres, но в целом это может быть MergeTree Clickhouse или файлы на диске в parquet-формате.

* Снимок состояния дает нам уверенность в консистентности данных, используемых для построения аналитического слоя.

* Данные raw-слоя могут быть использованы для расследования инцидентов загрузок. В реальных условиях стоит определить ttl хранения данных в raw-слое.

* Загрузка выполняется как `insert into ... select ...`.

* Если в процессе переноса в raw-слой возникает ошибка, то процесс ETL останавливается с записью в аудит.

## Этап raw -> core
[loader_core.py](../etl/loader_core.py)

* Core-слой содержит очищенные эталонные данные сделок, актуальные на момент запуска ETL-процесса. 

* Core хранит одну актуальную версию каждой сделки (без версионирования). Данные накапливаются за все периоды, по которым выполнялись загрузки. 

* Логика перезаписи словарей в core-слое:
  * загрузка словарей выполняется как `INSERT INTO core.dict ... from raw.dict ... ON CONFLICT ... DO UPDATE SET ...`.

* Логика перезаписи сделок в core-слое зависит от режима запуска ETL:
  * `--run-type incremental` 
    * загрузка сделок выполняется как `INSERT INTO core.price ... ON CONFLICT (price_id) ... DO UPDATE SET ...`.
    * таким образом происходит добавление и точечное обновление сделок.
  * `--run-type backfill`
    * Перед вставкой строк из таблицы `core.price` удаляются записи по `loading_date`.
    * таким образом происходит пакетное обновление сделок.

* Если в процессе переноса в core-слой возникает ошибка, то процесс ETL останавливается с записью в аудит. Изменения в core-слое откатываются.

* Строки с аномалиями записываются в `dq.quarantine_prices`.

* [Правила очистки и обогащения данных при переносе в core-слой](./core_rules.md)


## Этап core -> mart
[loader_mart.py](../etl/loader_mart.py)

- Слой mart содержит витрину «Карточка маршрута и коридор рыночных ставок».
- Разрез: месяц × город отправления × город назначения × группа кузова × весовая категория.
- Источник: `core.price` x `core.price_dates` x `core.price_body_group`.
- Только прямые завершённые перевозки (`is_fact`, не `complex`), `outlier_mark = false`, `price_rub > 0`, `distance > 0`.
- `body_group_id = 0` означает «Не указан» (не соответствует строке в core.body_group).
- Витрина пересобирается полностью при каждом запуске ETL (`truncate`) в случае запуска `--run-type backfill`.
- При инкрементальном запуске витрина пересобирается за 2 последних месяца.

### Правила очистки при переносе в mart-слой:

| Нарушение | Комментарий |
|-----|------------|
| outlier_mark = true | Исключаются статистические выбросы по флагу |

### Правило вычисления reliability_level

| Условие | Значение |
|-----|------------|
| trips_count >= 30, carriers_count >= 5 и свежесть последнего месяца не более 30 дней относительно as_of | HIGH |
| trips_count >= 10 | MEDIUM |
| иначе | LOW_DATA |

## Критерии приемки
- Слой RAW версионируется по номеру запуска ETL.
- Слой DQ версионируется по номеру запуска ETL.
- Каждый запуск ETL идемпотентный в слоях CORE, MART.
- Справочник городов дедуплицирован по gc_id.
- Сделки в слое CORE очищены по бизнес-правилам.
- Сделки в слое CORE содержат основной кузов в main_body_type_id и соответствующий родительский тип в price_body_group.
- Сделки в слое MART очищены по бизнес-правилам.
- Витрина сделок не содержит месяцев > месяца as_of.
